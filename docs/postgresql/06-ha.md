## 構成と障害ドメイン

物理ストリーミングレプリケーションでprimaryとstandbyを構成します。別ホスト/ゾーンに置き、同じDockerホスト内の2コンテナーをホスト障害対策とはみなしません。

<a id="section-2"></a>

## 同期方式と読み取り整合性

既定は非同期で障害時に未転送WALが失われ得ます。同期構成は待機対象とsynchronous_commitを設計し、書き込み可用性とレイテンシの増加を評価します。

<a id="section-3"></a>

## 昇格・接続先切り替え・再参加

監視・昇格・接続先切り替えはPostgreSQL単体では自動完結しません。昇格判定、旧primaryの隔離、アプリ再接続、旧ノードのpg_rewind/再同期を手順化します。

<a id="section-4"></a>

## 遅延監視とスプリットブレイン対策

pg_stat_replicationとpg_stat_wal_receiver、送信/flush/replay位置を比較します。遅延秒数だけでなくLSN差とslotのWAL保持量を見て、二重primaryを防ぐfencingを設けます。

<a id="section-5"></a>

## RPO・RTOと障害試験

primary停止・ネットワーク分断・standby遅延で、確定した書き込みの残存と再接続時間を測ります。DatabaseLaboratoryは1台構成なので、この障害試験には別の複数ノード環境が必要です。

<a id="examples"></a>

## 確認用の例と検証手順

```sql
SELECT pg_is_in_recovery();
SELECT application_name,state,sync_state,sent_lsn,write_lsn,flush_lsn,replay_lsn
FROM pg_stat_replication;
```
DatabaseLaboratory単体ではレプリカ行は0件です。空の結果を障害と誤認しないよう構成台帳と照合します。

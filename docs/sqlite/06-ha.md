## 構成と障害ドメイン

標準SQLiteにサーバーreplicaの選出やHA cluster機能はありません。アプリ/ストレージ側でwriterの所有権と復旧先を設計します。共有ファイルを複数ホストで書かせるだけでは冗長化になりません。

<a id="section-2"></a>

## 同期方式と読み取り整合性

WALは同一ホスト内の共有メモリ前提を持ち、ネットワークファイルシステム上で一般的なHA共有ストレージとして扱いません。外部複製方式の整合性を別に評価します。

<a id="section-3"></a>

## 昇格・接続先切り替え・再参加

writer停止確認、旧writer隔離、一貫したbackup復元、アプリのファイルパス切替、新writer起動の順を決めます。二重writerや古いfile handleを残さないようにします。

<a id="section-4"></a>

## 遅延監視とスプリットブレイン対策

アプリのlease/owner、最終backup時刻、配信遅延、ファイル世代とchecksumを監視します。DB単体にquorumがないため外部の所有権管理が必要です。

<a id="section-5"></a>

## RPO・RTOと障害試験

アプリcrash、ディスク故障、backupからの復元、二重起動防止を試験します。RPOは採用したbackup/外部複製に依存し、WALを有効にするだけでRPO=0とはなりません。

<a id="examples"></a>

## 確認用の例と検証手順

標準機能での練習は、書込みアプリ停止→backup生成→別パス復元→読書き再開です。ネットワーク共有へ同じDBを置いて複数writerを起動する試験とは分けます。

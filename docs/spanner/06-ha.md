## 構成と障害ドメイン

regional/dual-region/multi-region等の構成と投票/非投票/読み取りreplicaを理解し、地理配置と障害要件から選びます。Dockerでstandbyを追加する仕組みとは異なります。

<a id="section-2"></a>

## 同期方式と読み取り整合性

同期複製とquorumでcommitを確定し、strong read/stale readの選択をします。leaderからの距離と書込みレイテンシ、地域障害時の利用可能性を評価します。

<a id="section-3"></a>

## 昇格・接続先切り替え・再参加

サービス内のleader/failoverをアプリのsession再作成・transaction retryと分けます。DNSやDB名の切り替えが必要なDR復元時は別に手順化します。

<a id="section-4"></a>

## 遅延監視とスプリットブレイン対策

Cloud Monitoring、availability、replica/leader情報、client retry/abortを監視します。外部CDC consumerや配信先まで同時に冗長化されるとは限りません。

<a id="section-5"></a>

## RPO・RTOと障害試験

構成と契約の可用性条件を確認し、アプリの再試行・多地域障害・復旧を検証します。エミュレーターの再起動はインメモリ消去で、本番HAやRPO試験の代わりにはなりません。

<a id="examples"></a>

## 確認用の例と検証手順

エミュレーター停止→再起動後に、初期化サービスがschemaと1200件を再生成することを確認済みです。これは機能検証の再現性の確認です。本番ではregion構成とclient retryを用いた可用性試験を別途実施します。

# Rava: スコープに基づくメモリ管理を持つJava派生言語

提案日: 2026-10-13 / 状態: 初期設計案 / 実装言語: Rust

## 1. 提案の要点

Javaの構文とオブジェクト指向モデルの一部を引き継ぎ、**スレッドが所有する領域（region）、静的な寿命解析、値コピー、明示的なオブジェクトグラフのコピー**を組み合わせたAOTコンパイル言語を実装する。プロジェクト名に合わせ、以下ではRavaと呼ぶ。

Rustと共有する目標は、スコープの終了に連動した決定的な解放と、解放後参照の防止である。通常のJavaクラスでは可変な別名参照を許すため、Rustの借用規則をそのまま適用する設計にはしない。オブジェクトごとの所有権ではなく、原則として**領域を所有し、領域内のオブジェクトを一括解放する**。

実現可能性の前提は、Java全体の互換性を手放し、安全性を証明できないプログラムを拒否できることである。任意のJavaプログラムを変更なしで動かすこと、実行時間の上限、一般にGCより低いメモリ使用量は保証しない。

この提案では次を「GCなし」と定義する。

- 実行時に到達可能性を追跡して不要な言語オブジェクトを回収する処理を持たない。
- 言語オブジェクトの寿命を参照カウントで管理しない。循環参照の回収器も持たない。
- 領域の終了、値の寿命終了、メッセージ等の所有権終了によってメモリを解放する。
- コピー時のグラフ走査は明示操作であり、不要オブジェクトを検出する回収処理ではない。
- OSのアロケータ、Rustの`Vec`・`Box`、所有されたランタイム資源は使用できる。これらの解放契機と上限も管理する。

実装対象の詳しい規則は[メモリモデル](memory-model.md)、コンパイラ・ランタイム構成と検証方法は[実装計画](implementation-plan.md)に分ける。以下の「v0」は最初の実用プロファイルを指し、各開発段階ですべてを同時実装する意味ではない。

## 2. 採用する判断

| 論点 | v0の方針 | 引き受ける制限 |
| --- | --- | --- |
| 入力 | Java 17の構文・基本意味論を基準にした明示的なサブセット | 全言語機能、Java SE API、TCK互換を対象にしない |
| 実行形式 | 独自IRからネイティブコードを生成するAOT | JVM、JIT、`.class`実行器は作らない |
| 通常のclass | 参照代入・別名参照・同一性を維持 | 寿命を越える参照保存は禁止 |
| 値 | プリミティブと明示的な値型を積極的にコピー | 値型は通常のclassと異なる意味論を持つ |
| 割り当て | 最短の安全な領域へ静的に配置する | 推論不能時に無条件でスレッド領域へ逃がさない |
| 循環 | 同じ領域内で許可し、領域ごと解放 | 領域が生きている間の不要オブジェクトは回収しない |
| スレッド | スレッドごとの領域木と、コピーによるメッセージ通信 | 可変オブジェクトのスレッド間共有は禁止 |
| リフレクション | AOT時に登録した型だけを、現在のスコープ内で操作 | 動的クラスロード、任意の生成・呼出しは不可 |
| 例外 | スコープ参照を含まない所有された値ペイロード | 任意のJavaオブジェクトを保持するThrowableは不可 |
| 資源 | 明示closeと構造化cleanup | finalizer、Cleaner、参照キューには依存しない |
| jar | ソースの再コンパイルと資源の取り込みを優先 | バイナリjarのそのままの実行は対象外 |

Javaの参照の`==`は同一オブジェクトかを判定する。このため通常の代入を暗黙のdeep copyに変えると、更新の共有や同一性の観測結果が変わる。**値型は暗黙コピー、通常のclassは参照コピー、領域を越える複製は明示コピー**という境界を採用する。[Java Language Specification §15.21.3](https://docs.oracle.com/javase/specs/jls/se17/html/jls-15.html#jls-15.21.3)

## 3. 領域による解放

```text
プロセス定数領域 I（ビルド時に確定した不変データのみ）
├─ スレッド領域 T1
│  ├─ リクエスト領域 R1
│  │  └─ 一時領域 S1
│  └─ 次のリクエスト領域 R2（R1の終了後に作成）
└─ スレッド領域 T2
   └─ リクエスト領域 R3
```

同じスレッドでは、子領域のオブジェクトから同じ領域または祖先領域へ参照できる。親から子、兄弟間、別スレッドへの通常参照は許可しない。したがって子領域の終了時には、存続する領域から子への参照がない。領域内の循環を追跡する必要もない。

スレッド終了は最外側の解放境界である。サーバやスレッドプールでは、リクエスト・タスク・ループ反復ごとに子領域を終了させる。スレッド終了だけに解放を依存すると、長時間動作する処理でメモリが増え続ける。

この方式は到達不能オブジェクトを随時回収しない。長寿命のマップを更新し続ける用途、巨大な共有グラフ、無制限のキャッシュは初期の得意領域ではない。バッチ処理、パーサ、一時グラフ変換、独立したリクエスト処理を最初の対象にする。

## 4. 互換性の境界

| 機能 | v0の扱い |
| --- | --- |
| 算術、分岐、ループ、メソッド、パッケージ | 対応。評価順、整数の桁あふれ、null・配列境界検査等を仕様化 |
| class、継承、interface、仮想呼出し | 対応。overrideにも領域・副作用契約を要求 |
| 配列、コレクション | 領域付きで再実装。参照配列は要素型について不変（invariant）とし、要素の更新は可能。Javaの配列共変性は採用しない |
| generics | 不変な型パラメータから開始。raw type、wildcard、複雑な推論は後回し |
| String | 不変な参照型。リテラルは定数領域、動的文字列は通常領域。動的internは不可 |
| record | 対応時も通常の参照型。自動的に値型とは見なさない |
| ラムダ・クロージャ | 領域を持つ環境として実装。捕捉参照が保存先より長寿命であることを要求 |
| static | ビルド時に確定できるプリミティブ・深く不変な定数のみ。可変staticと副作用付きclass初期化は不可 |
| ThreadLocal | 自動変換しない。明示的なスレッド所有Contextを渡す |
| Thread、synchronized、wait/notify、volatile | Java APIとしては非対応。Rava専用のworker/channel APIを提供 |
| リフレクション | 登録型の限定APIを新設。通常のjava.lang.reflect全体は互換にしない |
| ClassLoader、動的proxy、実行時コード生成 | 非対応 |
| Weak/Soft/PhantomReference、finalize、Cleaner | 非対応 |
| Java Serialization、JNI、Unsafe、JVMTI | 非対応。FFIは別途、所有権契約付きの限定C ABIにする |
| 非同期処理 | v0はOSスレッド上の構造化worker。async/await、継続、スレッド間タスク移動は後続設計 |

`final`は参照先全体の不変性を意味しないため、`static final`なら任意のオブジェクトを共有してよいとはしない。共有定数にできるのは、コンパイラが推移的不変性を認定した型だけとする。通常のJavaコードと意味が変わる機能は、黙って変換せず、専用構文・型・診断で境界を示す。

### 既存jarの活用

1. **優先対象:** `sources.jar`や別途入手できるソースをRava向けに再コンパイルする。依存先まで解析でき、対応サブセットに収まる小さなアルゴリズムライブラリから採用する。
2. **資源:** jarをコンテナとして使い、設定・テンプレート・静的データを取り込む。資源取り込みとコード実行は区別する。
3. **後続候補:** 許可したclassファイルの一部を独自IRに変換するインポータ。命令・API・割当・例外・同期の全要素を検証できる場合だけ取り込む。これは限定的な変換機能でありバイトコード互換の約束ではない。v0の必須要件にはしない。
4. **対象外:** 任意の既存jarのリンク、逆コンパイルを前提とする互換性、JVMを埋め込むフォールバック。フレームワークを動かすためにGCを持ち込まない。

取り込むライブラリには、対応API一覧と割当先・参照保存・例外・スレッド効果の契約を付ける。契約がない外部コードは安全なコードとして呼び出さない。

## 5. 先行事例から採用する教訓

以下は一次資料で確認できる事実と、それを踏まえた本提案の設計判断である。先行研究全体を「失敗」と総括せず、どの制約の下で何が成立したかを見る。

| 事例 | 確認できる内容 | 本提案への示唆 |
| --- | --- | --- |
| RTSJ scoped memory | 領域単位の解放と、長寿命側への短寿命参照保存を防ぐ動的検査を持つ。通常のGC heapとも併存する | 領域間参照制約を基本規則にする。RTSJをJava全体のGC除去の実証とは扱わない |
| SafeJava系のregion・ownership型 | RTSJの検査を静的に保証する型システムを提案。長寿命スレッドの共有領域ではsubregionによる反復的解放も扱う | メソッド境界の領域契約と、スレッドより短い解放単位が必要 |
| Cyclone | regionと型・effect systemで寿命を扱う。論文の設計にはGC heapも含まれる | 注釈やプログラムの変更を許容し、自動解析だけで全例を扱おうとしない |
| GraalVM Native Image / Epsilon | AOT実行でもメモリ管理は別途必要。Epsilonは割り当てたメモリを回収しない | AOT化やGC停止だけを成果にせず、繰り返し処理で実際に再利用できることを検証する |

出典: [Oracle RTSJ解説](https://www.oracle.com/technical-resources/articles/javase/jsr-1.html)、[A Type System for Safe Region-Based Memory Management in Real-Time Java](https://people.csail.mit.edu/rinard/techreport/MIT-LCS-TR-869.pdf)、[Region-Based Memory Management in Cyclone](https://www.cs.cornell.edu/projects/cyclone/papers/cyclone-regions.pdf)、[GraalVM Memory Management](https://www.graalvm.org/dev/reference-manual/native-image/optimizations-and-performance/MemoryManagement/)。

## 6. 初期の達成条件と限界

最初の実用例は、独立した要求をworkerで処理し、解析用の循環グラフを要求領域に作り、結果を値または明示コピーで返す小さなサービスとする。登録型の反射生成、エラー経路、メッセージ受信後の送信元スレッド終了まで確認する。

採用の判断には、正しさに加えて次を測る。

- 同じサイズの要求を反復しても、タスク終了後の生存領域数・使用バイト数が増え続けない。
- 値コピー・グラフコピーの回数、バイト数、時間と最大一時メモリ量が観測できる。
- 領域終了に伴う解放時間、外部資源cleanup時間、p50/p95/p99の処理時間を分離して測る。
- 実用例で必要だった領域注釈、明示コピー、ソース修正の箇所を記録する。

GCの休止はなくても、大きなコピー、一括解放、OSの割当、ページフォルト、スケジューリングによる遅延は残る。領域を小さく分けることで扱いやすくするが、hard real-time性や既存JVMに対する性能優位は、計測前に主張しない。

最初に証明すべきなのは「広いJava互換性」ではなく、選んだサブセットにおける寿命規則の健全性と、長時間動作時のメモリの再利用である。その確認後に、互換性と最適化を段階的に広げる。

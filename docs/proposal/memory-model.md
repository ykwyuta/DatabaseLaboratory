# メモリモデルと静的解析

[提案概要](README.md) / [実装計画](implementation-plan.md)

## 1. 用語と保証範囲

- **領域（region）:** 複数の割り当てを所有し、終了時にまとめて破棄する単位。
- **割当領域:** オブジェクトが生成されてから破棄されるまで所属する領域。参照のcastや代入では変わらない。
- **参照の利用期間:** ローカル変数や一時的な借用を通じて、その参照を利用できる期間。割当領域とは別に追跡する。
- **outlives:** `A ⪰ B`を「AがBの全生存期間を包含する」と定義する。等しい領域も含む。
- **領域capability:** 生きている領域への割り当て等を許可するコンパイラ管理の権限。通常のJavaオブジェクトではなく、保存・コピー・スレッド転送はできない。

スレッド内の領域は厳密な木構造とし、子は親の終了前に終了する。再帰呼出しやループ反復では、同じソース位置でも別の動的領域インスタンスを作る。静的region IDと実行時インスタンスIDを同一視しない。

安全な言語コードには、解放後参照、二重解放、通常オブジェクトを介したデータ競合が起こらないことを目標にする。この保証は型・領域検査器、IR verifier、ランタイム、許可したFFIの正しさを前提とする。Rustで実装しただけで対象言語の安全性が得られるわけではない。

## 2. 参照を保存する規則

オブジェクト`x`の領域を`R(x)`とすると、`x.field = y`には次を要求する。

```text
R(y) ⪰ R(x)
```

nullには領域がなく、保存可能とする。同じスレッド内でこの条件を満たすのは、同じ領域または祖先領域への参照である。プロセス定数領域への参照は特別に許可する。

この規則をフィールド、配列要素、コレクション内部、クロージャの捕捉環境、反射による書き込みに等しく適用する。局所変数についても、保持する参照の利用期間が参照先の生存期間に収まることを検査する。単にフィールド代入だけを検査してはならない。

| 参照元 | 参照先 | 判定 |
| --- | --- | --- |
| 同一領域 | 同一領域 | 許可。別名参照・可変参照・循環も可 |
| 子領域 | 祖先領域 | 許可 |
| 親領域 | 子領域 | 拒否 |
| ある子領域 | 兄弟領域 | 拒否 |
| スレッドT1 | スレッドT2 | 拒否。通信APIを利用する |
| 任意の通常領域 | ビルド時の不変定数領域 | 許可 |

通常オブジェクトの解放は領域単位であり、`free(object)`やユーザーによる領域の途中resetは提供しない。領域終了時は内側から終了し、存続するオブジェクトから当該領域への辺がないため、一括破棄できる。領域をまたぐ循環もこの規則によって生じない。

定数領域へ置けるのは、コンパイラが推移的不変性を認定した型だけとする。すべての到達可能フィールドが不変で、可変配列、変更メソッド、内部の可変状態を持たず、可変型へcastできないことを検証する。単にビルド時に普通の可変classを生成しただけでは共有定数にできない。Stringの内部表現等は専用の検証済み不変表現を使う。

### 割当領域を短く見せることはできない

内側のスコープで外側のオブジェクトを借りても、そのフィールドの保存先は外側のままである。内部表現では`Ref<T, allocation_region, borrow_lifetime>`を区別し、可変オブジェクトの割当領域パラメータは不変（invariant）として扱う。borrow期間を短くすることと、オブジェクトの割当領域を書き換えることを混同しない。

`Object`への変換、generics、interface、cast、配列、反射を通じても割当領域情報を失わせない。正確な領域が静的に不明なら、領域を隠した参照とoutlives制約を保持し、証明できない書き込みを拒否する。動的型が不明だから寿命検査を省く、という経路は設けない。

## 3. ソース上の表現と例

以下は**未実装の仕様を説明する擬似コード**である。`scope (r)`、`new (r)`、`value class`、領域注釈の最終文法は別途決める。Java標準構文として実行できることは意図しない。v0では明示領域指定を先に実装し、後で通常の`new`からの推論を加える。

### 同じ領域内の共有と循環

```java
scope (request) {
    Node a = new (request) Node();
    Node alias = a;
    Node b = new (request) Node();
    alias.next = b;
    b.next = a;
    assert a == alias;       // Javaの参照同一性を維持
    assert a.next == b;
}                           // 循環を走査せず領域全体を破棄
```

### 外側への参照保存は拒否

```java
scope (outer) {
    Holder holder = new (outer) Holder();
    scope (inner) {
        Node local = new (inner) Node();
        Holder borrowed = holder;
        borrowed.node = local;   // E_REGION_ESCAPE
        // borrowedの利用期間はinnerでも、Holderの割当先はouter
    }
}
```

修正は、`Node`を最初から`outer`に作る、`copyTo(outer, local)`で複製する、または`Holder`も`inner`に配置することである。どれを選ぶかは共有関係と必要な寿命によって変わるため、コンパイラが黙ってdeep copyに置換しない。

### 戻り値を呼出し元の領域に直接構築

```java
@Alloc("result")
@Returns("fresh:result")
Node build(@RegionParam Region result, int value) {
    return new (result) Node(value);
}

scope (request) {
    Node result = build(request, 42);
    consume(result);
}
```

`Region`は説明用のcapabilityであり、普通の可変オブジェクトではない。領域引数は型検査後に隠し引数として渡せる。最初から呼出し元の領域に割り当てるため、既存オブジェクトの移動やidentityの変更は起こらない。

メソッドの戻り値は「値」「引数・receiver由来の参照」「指定した結果領域に新規生成」のいずれかを契約に持つ。呼出し先の一時領域で作った参照をそのまま返す契約は認めない。

## 4. コピーを活用する範囲

### 4.1 値型

プリミティブと明示された値型は、代入・引数・戻り値で値コピーする。v0の値型には次の制限を設ける。

- フィールドはプリミティブまたは別の値型のみ。有限の固定サイズで、再帰的な参照を持たない。
- 不変で、継承、null、参照同一性、monitor、資源の所有を持たない。
- 通常の`Object`のサブタイプにせず、暗黙boxingは行わない。
- `==`はフィールドごとの値比較。浮動小数点はプリミティブの比較規則に従う。

```java
value class Point { int x; int y; }
Point p = Point(10, 20);
Point q = p;                 // 小さな値をコピー
```

初期はサイズが既知の座標、トークン、識別子、固定長DTO等を対象にする。可変長文字列・配列を含む所有値型は、dropやmoveの仕様が別途必要なため後続とする。大きな値コピーにはサイズ診断を出し、ABIの間接渡しや最適化によるコピー除去を可能にする。

普通の`class`、Javaの`record`、動的`String`を暗黙に値型へ変更しない。小さなclassをスタックに置く最適化を行っても、言語上の別名参照と同一性は維持する。

### 4.2 通常オブジェクトのグラフコピー

`copyTo(destination, source)`は、明示された領域へグラフを複製する操作である。実際に複製する非定数オブジェクトには元と異なるidentityを与え、共有するビルド時の不変定数は同じidentityを保つ。root自身が不変定数なら元の参照を返す。自動生成できる`@GraphCopy`契約を持つ型と、共有可能な不変定数に限定する。

1. コピー開始前に元参照が有効で、destinationが現在のスレッドの有効な領域であることを確認する。
2. sourceから到達する**全参照先**をコピーする。祖先領域への参照も対象とし、ビルド時の不変定数だけ共有を許す。
3. 元オブジェクトIDから新オブジェクトIDへの対応表を使い、内部の別名参照と循環を保存する。動的な型も保存する。
4. コンストラクタ、getter、任意のユーザーcopy hookを呼ばず、検証済みレイアウトに従ってフィールドを複製する。
5. 資源、channel endpoint、thread、scope capability、native pointer、コピー非対応の動的型を含むグラフは拒否する。型が隠れている場合も実行時descriptorで確認する。
6. 非公開の割当batchに構築し、全体が成功した場合だけdestinationへ組み込み、根参照を公開する。失敗時はbatchを破棄し、途中グラフを外から観測できないようにする。

この操作中はユーザーコードやコールバックを実行しないため、単一スレッド所有の元グラフは変化しない。コピー先の参照辺は同じdestinationか不変定数だけになり、元スコープの終了から独立する。

`@GraphCopy`は明示的な参加契約であり、任意のclassが自動的に対応するとはしない。identity・アドレスから計算したキャッシュ等を保持しないことを要求する。コンパイラは型の構造と禁止資源の不包含を検査するが、任意のユーザー定義不変条件までは証明しない。契約が誤っていてもメモリ安全性の規則は維持し、コピー後の意味的な正しさは型の契約と試験で確認する。

標準Mapはこの問題を避けるため、v0ではキーを整数、真偽値、それらからなる値型、標準Stringに限定し、内容に基づく安定したhashと等価性を使う。identity依存のキー、任意のユーザー定義hash、インスタンス固有seedに依存した保存状態を初期仕様に含めない。Mapのコピー後にも検索が成立することを専用試験で確認する。

```java
scope (outer) {
    Node kept;
    scope (inner) {
        Node a = new (inner) Node();
        a.next = a;
        kept = copyTo(outer, a);
        assert kept != a;
        assert kept.next == kept;
    }
    consume(kept);          // inner終了後も有効
}
```

別々のcopy呼出し間では、非定数オブジェクトの共有関係を保持しない。複数のroot間の共有を保ちたい場合は、それらを一つのrootコンテナにまとめて一回でコピーする。オブジェクト数をV、参照辺数をE、配列や文字列等を含むpayloadの総バイト数をBとすると、全体のコピー時間は`O(V + E + B)`、対応表は`O(V)`、コピー本体のメモリは総バイト数に比例する。走査は明示的な作業キューを用い、深い再帰でホストスタックを消費しない。

祖先参照を辿って予想外に巨大なグラフをコピーする可能性がある。ノード数・バイト数・作業領域に上限を設け、実績を表示する。必要に応じてアプリケーションが小さなDTOへ変換する。shallow copyによって短寿命参照を残す方式は採用しない。

### 4.3 移動と昇格

一般のJavaオブジェクトにはaliasが存在し得るため、生成済みグラフの無条件なmove、動的な親領域への昇格はv0では提供しない。コンパイラが割当時に親を選ぶことと、割当後に所属を変えることは区別する。

一意所有が証明された独立領域の移譲、コピー省略、可変長所有値は後続の最適化候補とする。初期の安全性やスレッド通信をその実現に依存させない。

## 5. 静的解析

### 5.1 解析の順序

1. 型付きHIRを構築し、ローカル変数、割当箇所、フィールド、引数、戻り値、捕捉環境に領域変数を付ける。
2. 明示scope、メソッド呼出し、ブロック、ループ反復を候補となる寿命境界として構築する。
3. 参照代入・保存・呼出し・返却・捕捉からoutlives制約と領域等式を生成する。
4. ポイント先とescape情報を保守的に求め、関数要約を呼出グラフの再帰SCCごとに固定点まで計算する。
5. 許可された候補の中で最も短い領域を選ぶ。領域間の関係が確定しない場合は明示契約を要求する。
6. CFGの全出口にcleanupを付け、領域操作を明示したMIRを独立verifierで検証する。

一般プログラムの正確な寿命を自動発見できるとは仮定しない。証明できない安全なコードを拒否することは許容し、証明できないコードを安全と推定して通すことはしない。

### 5.2 推論できる範囲を制限する

暗黙の`new`は現在のメソッド内の安全な領域へ配置する。返却用の割り当ては、明示または検証済みの結果領域契約がある場合だけ呼出し元へ直接構築できる。

要求・タスク・明示scopeには「ここより長寿命に割り当てない」という境界を設定する。そこを越える割り当ては、明示capabilityまたは関数の割当効果契約を必要とする。解析が難しいことを理由にスレッド領域や定数領域へ自動昇格しない。

ループでは、反復をまたがない割り当てを反復領域へ置く。累積結果は明示した親領域へ作る。ループ内で親領域への割り当てがある場合は、ソース位置と推定できる増加要因を診断する。領域寿命を確定できても、割当量の有限な上限を一般に証明できるとは限らない。

### 5.3 メソッド契約

メソッド要約は少なくとも以下を持つ。

| 情報 | 例 |
| --- | --- |
| 領域パラメータと制約 | `arg_region ⪰ receiver_region` |
| 参照の保存先 | 引数をreceiver.fieldに保存、保存なし |
| 返却参照の起源 | 引数由来、receiver由来、結果領域への新規生成 |
| 割当効果 | `alloc(result)`、一時領域だけに割当 |
| 変更効果 | receiverを変更、引数を読み取りだけ |
| 特殊効果 | copy、throw、channel送信、native呼出し |

内部メソッドは推論し、公開APIと外部ライブラリには検証済み契約を出力する。overrideは基底より強い前提条件を要求せず、許可された保存・割当・変更効果を増やさず、返却保証を弱めない。closed-worldの仮想呼出しでも、この規則を省略しない。

再帰、別コンパイル、間接呼出しで解析上限に達した場合は、原因と要求される契約を診断する。ソースと契約のハッシュ・コンパイラ仕様版を結び付け、古い要約を別の実装に適用しない。

### 5.4 診断の要件

エラーは単なる「borrow失敗」ではなく、保存先、参照先、領域境界と修正候補を示す。

```text
E_REGION_ESCAPE: holder.node は outer 領域に保存されます
  local の割当領域: inner（このブロックの終了時に解放）
  必要な関係: region(local) outlives outer
  候補: outerに直接構築 / copyTo(outer, local) / holderをinnerへ移す
```

配置先一覧とcopy挿入・省略のレポートも用意する。通常classへの暗黙deep copyは行わないので、レポート中の暗黙コピーは値型または言語で定義された通信・例外処理に限られる。

## 6. スレッドとメッセージ

各OSスレッドに一つの所有Contextとルート領域を設ける。別スレッドの領域capabilityや通常参照は渡せない。共有可能なのはビルド時の深く不変な定数と、専用のランタイム同期オブジェクトのハンドルだけとする。

通信は次の手順に固定する。

1. `sendCopy`は値または`@GraphCopy`グラフを、参照アドレスを含まない所有されたメッセージ表現へ複製する。内部の循環・共有はメッセージ内IDで表し、共有する不変定数は同じ実行イメージ内の定数IDで表す。
2. キューがそのメッセージを一意に所有する。送信元のスコープ・スレッドの終了は影響しない。
3. `receiveInto(currentTask)`は現在の受信タスク領域に復元してから、キューの所有メモリを破棄する。受信途中の失敗では部分グラフを公開しない。
4. キャンセル、受信側終了、キュー破棄でも残ったメッセージを決定的に破棄する。

v0では送信時・受信時の二回のデータ移送を許容する。零コピー共有やregion移譲は後続とする。メッセージの順序は単一送信者からのFIFOとし、成功した送信と対応する受信に同期関係を設ける。Java Memory Model全体への互換性は主張しない。

キューは要素数だけでなく合計バイト数にも上限を設ける。満杯時は非ブロッキングAPIが`QueueFull`を返すことを基本とし、待機APIには期限・キャンセルを持たせる。エンドポイントとキュー所有者を分ける。終了時は送受信をcloseしてキャンセルを通知し、待機者を起こし、workerをjoinし、未処理messageとキューを破棄する順にする。キューを所有する構造化worker群の外へエンドポイントを逃がさない。言語オブジェクトの参照カウントでキュー寿命を管理しない。

workerはタスク開始ごとに子領域を作り、成功、失敗、協調的キャンセルのいずれでも終了させる。強制的なthread killは提供しない。スレッド終了時はすべての子領域、スレッド資源、ルート領域を内側から破棄する。

## 7. スコープに閉じたリフレクション

型名から扱える型・フィールド・メソッドをAOT時に登録する。型メタデータは不変定数領域に置く。実行時に未知のjarやclassをロードしない。

`reflect(currentScope)`のcapabilityは現在のスレッド・現在の領域だけで有効とする。v0では以下に限定する。

- インスタンス生成の割当先は現在の領域。登録コンストラクタにも現在領域とその子に限定した割当・変更効果契約を要求し、祖先の可変オブジェクトを変更させない。
- インスタンス操作対象は現在の領域のオブジェクトのみ。祖先の可変オブジェクトを反射で変更しない。
- 呼出し可能メソッドは、現在領域とその子への割当・変更だけを行う契約を持つ。未知のnative、非同期起動、外側への割当・保存を行うメソッドは登録不可。
- 入力の参照も通常のoutlives規則に従う。返却参照・反射wrapperの利用可能期間はcapabilityの期間以内とする。
- `Field.set`相当の操作は、型、実際のreceiver領域、参照先領域、スレッド所有者、世代を実行時に検査する。失敗時は変更前に`ScopeViolation`を返す。

フィールド読出しで祖先領域のオブジェクトが返る場合も、反射wrapperは現在スコープを越えて保存できない。安全な公開型へ変換する場合も割当領域情報を維持する。外側へ結果を残す操作は、スコープ終了前の明示`copyTo`または値への変換に限定する。

「割当先を現在領域にする」だけでは、外側のオブジェクトへの書き込みによるescapeを防げない。通常経路は静的に保証し、動的な対象を持つ反射境界には実行時検査を残す。この検査は領域関係の確認であり、GCではない。

## 8. 例外と外部資源

### 8.1 例外は独立した所有ペイロード

v0の例外型は、通常の参照classから区別した組込のエラー型とする。エラー型に格納できるのはプリミティブ、値型、コピー済みテキスト、所有された原因情報だけで、通常領域への参照は許可しない。Javaの任意のThrowableサブクラスや例外オブジェクトの同一性は非対応とする。

throw時にランタイム所有の`ErrorPacket`を構築し、スコープのunwind中はランタイムが一意に所有する。catchはcatchの期間だけpacketを借用する。再throwはpacketの所有権を移し、catch終了で処理済みpacketを破棄する。catch外へ保存する場合は、必要な情報を値または指定領域へ明示コピーする。

これによりthrow元の領域を解放しても、catchから解放済み領域を参照しない。例外をスレッド領域へ蓄積する方式は採用しない。原因情報・抑制例外・スタック位置情報には個数とバイト数の上限を設け、オブジェクト参照をスタックトレースに保持しない。

Rustのpanicを言語例外の実装契約にはしない。MIRでは成功・例外の継続先を明示し、native ABIでもstatusと所有packetの受渡しを明示する。メモリ枯渇は確保済みの小さなエラー情報で報告し、それも不可能な内部障害はfail-fastとする。

回復可能な範囲は、言語上の割当予算超過と、明示的に失敗を返せるruntimeの確保経路とする。コピーの対応表・作業キュー・メッセージ等もfallibleな確保を用いる。OSによる強制終了、ホストアロケータのabort、runtime内部の致命的障害までcleanupを保証するものではない。

### 8.2 cleanupの順序

`return`、`throw`、`break`、`continue`、通常終了のすべてにcleanup edgeを生成する。内側の資源を閉じ、対応する`finally`を評価し、そこでまだ参照できる領域を保ったまま、構文上の終了順に領域を破棄する。

`finally`による戻り値・例外の置換、try-with-resourcesの逆順closeと抑制例外を仕様化する。領域破棄後に`finally`が同じ領域を参照する順序は許されない。新しい例外で置換された古いpacketも破棄する。

### 8.3 資源の解放とメモリの解放を分ける

ファイル、socket、native buffer等はコピー不可の所有resource型で管理する。resourceの所有者は一つとし、非所有の一時借用だけを許す。try-with-resources相当の構文でcloseし、領域終了時にはランタイムの非送出cleanupを最後の保護として実行する。明示close時には登録を解除し、二重closeを防ぐ。

closeはresourceの所有権を消費し、生きている借用がある間は呼び出せない。借用を所有者より長く保存することも禁止する。例えば`view = buffer.borrow(); buffer.close(); use(view);`は静的に拒否する。自動cleanupの位置でも同じ規則を要求し、普通の領域参照とresourceの借用は別の型として検査する。

通常classに任意のデストラクタやfinalizerは設けない。領域内に循環があってもユーザー定義の破棄順を決める必要がないようにする。Rustの独立したheapを所有するランタイム値をarenaへ格納する場合は、専用cleanup登録でdropする。arenaのページ破棄だけで`Vec`等の内部割当まで解放できるとは仮定しない。

プロセス強制終了時にユーザーcleanupが動く保証は置かない。FFIはv0のコア外とし、追加時には借用ポインタの呼出し後保持禁止、明示release、スレッド制約、コールバックの寿命を個別契約にする。

## 9. メモリ量と保持の限界

`list.remove(x)`や参照の上書きで到達不能になっても、同じ領域内の領域割当はその場で回収されない。可変長コレクションの拡張で使わなくなったarena bufferも領域終了まで残り得る。長寿命のrootへ追加と削除を繰り返す処理は、安全でもメモリ効率が悪い。

初期は要求・バッチ単位の領域、容量予約、上限付きコンテナを利用する。長寿命データの再構築は、古い子領域を生かしている間に小さな値・所有メッセージ表現へ必要データを退避し、終了後の新しい領域へ復元する。兄弟領域への直接参照や、外部aliasを残したままのresetは認めない。

解放は「ランタイムが再利用可能にする」ことであり、RSSが直ちに低下することではない。ページpoolには上限を設け、使用量と予約量を分離して報告する。スレッド・要求・メッセージ・例外・コピー作業領域の予算を別々に管理する。

各領域とキューに実際のバイト上限を設け、同時数を制限できれば、概算上限は次のように分解できる。

```text
プロセス定数・コード
  + 各スレッドのroot上限とスタック
  + 同時に生きる全子領域の上限（祖先も含む）
  + キュー上限 + 実行中のコピー/復元/例外の作業予算
  + 上限付きpool・メタデータ・アロケータの余剰
```

これは無制限の再帰やユーザー指定の大きな上限まで自動的に抑える保証ではない。解析が保証する寿命の正しさと、容量設定・負荷試験が確認するメモリ上限を区別する。

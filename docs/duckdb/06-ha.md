## 構成と障害ドメイン

標準embedded DuckDBにleader選出・standby昇格のHA機能を期待しません。アプリ/ジョブの冗長化と、読み取り用のimmutable snapshot配布を設計します。

<a id="section-2"></a>

## 同期方式と読み取り整合性

同じnativeファイルへの複数プロセスwriterではなく、単一writerと公開世代を基本にします。複数readerが同一のmanifest/ファイル集合を参照する整合性を決めます。

<a id="section-3"></a>

## 昇格・接続先切り替え・再参加

writer停止/隔離→最後の確定世代を開く→ジョブ/接続先を切替→未完了処理を再実行する手順を持ちます。古いwriterの二重公開をlease等で防ぎます。

<a id="section-4"></a>

## 遅延監視とスプリットブレイン対策

公開世代、最終成功時刻、file hash、ジョブ状態、復旧元の可用性を監視します。shared storageを置くだけで単一writerの所有権が解決するわけではありません。

<a id="section-5"></a>

## RPO・RTOと障害試験

ジョブcrash、DB/外部ファイル喪失、二重起動、公開途中失敗を試します。RPOはsnapshotの公開頻度、RTOは再ロードや分析warm-upを含めて測ります。

<a id="examples"></a>

## 確認用の例と検証手順

標準機能の検証では、確定ファイル世代を複製して読取り専用で開き、writer crash後に最後の世代へ切り替えます。同じnative DBへ複数ホストからwriterを接続する試験とは分けます。

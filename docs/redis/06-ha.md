## 構成と障害ドメイン

primary/replicaとSentinelによる監視・昇格、Clusterによるslot分割を区別します。Clusterは各shardのreplicaと複数ノードの可用性設計が必要です。

<a id="section-2"></a>

## 同期方式と読み取り整合性

複製は非同期で、障害時にack済み書込みが失われ得ます。WAITは受信確認を補助しますが強整合性や全障害での無損失を保証する仕組みではありません。

<a id="section-3"></a>

## 昇格・接続先切り替え・再参加

Sentinel対応クライアントやCluster routing、再接続、MOVED/ASK、旧primary隔離を試験します。再参加ノードのデータは現primaryから再同期する前提を明確にします。

<a id="section-4"></a>

## 遅延監視とスプリットブレイン対策

INFO replicationのoffset/lag/link、replication backlog、Sentinel quorumを監視します。部分再同期が不可能な場合のfull syncと、そのメモリ/ネットワーク負荷を評価します。

<a id="section-5"></a>

## RPO・RTOと障害試験

primary停止・ネットワーク分断・backlog超過で、データ損失と再接続を測ります。DatabaseLaboratoryは単体で、自動昇格やClusterのroutingは構成していません。

<a id="examples"></a>

## 確認用の例と検証手順

```text
ROLE
INFO replication
```
別構成でreplica停止、primary喪失、full/partial resyncを試験します。

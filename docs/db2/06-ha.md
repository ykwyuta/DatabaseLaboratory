## 構成と障害ドメイン

HADRはprimaryからstandbyへログを送信・再生します。pureScaleの共有データ構成やpartitioningとは目的が異なり、Community版の対応条件・制限を確認します。

<a id="section-2"></a>

## 同期方式と読み取り整合性

SYNC/NEARSYNC/ASYNC/SUPERASYNCのack条件を比較し、転送待ち・データ損失・ネットワーク遅延のトレードオフを決めます。peer状態だけで全障害時の損失0と結論しません。

<a id="section-3"></a>

## 昇格・接続先切り替え・再参加

planned takeoverとforced takeoverを分けます。旧primaryを隔離し、Automatic Client Reroute等の接続切替、旧ノードの再同期と再参加を確認します。

<a id="section-4"></a>

## 遅延監視とスプリットブレイン対策

MON_GET_HADR、db2pd -hadr、log gap/peer state/接続状態を監視します。外部クラスタマネージャーとquorum/fencingが自動昇格の安全性を左右します。

<a id="section-5"></a>

## RPO・RTOと障害試験

ログ転送断、standby再生遅延、primary停止を試し、最後にcommitしたキーと再接続時間を記録します。Ravaにはstandbyやcluster managerを含めません。

<a id="examples"></a>

## 確認用の例と検証手順

```text
db2pd -db RAVA -hadr
```
未構成ならHADR情報がない状態です。複数ノード環境でのみtakeover試験を行います。
